# Composition Designer — 未实现功能显性化与授权阻塞治理规范

> 文档类型：项目工作流改进提案  
> 日期：2026-11-27  
> 适用范围：Composition Designer 的 AI Agent 任务执行、任务汇报、任务卡、执行计划与授权管理  
> 状态：Proposed，待项目维护者确认  
> 关联：`AGENTS.md`、`working/plan.md`、`working/tasks/`、`changes/`、`docs/adr/`

---

## 1. 问题定义

当前工作流的问题不是 AI 擅自越权，也不主要是 AI 直接跳过任务，而是：**当实现过程中发现某项能力超出当前授权范围时，AI 会将该能力搁置，继续完成授权范围内的工作；但在最终汇报中，对已完成功能、测试和实现细节描述得很充分，对因授权不足而未实现的功能却往往只用一句简短的“遗留问题”带过。**

这会造成明显的信息不对称：

- 已完成内容有详细证据，用户容易判断任务进展；
- 未实现内容被压缩在结果末尾，缺少独立标题、影响说明和决策请求；
- 用户难以识别哪些功能只是暂缓，哪些已经不再计划，哪些必须取得额外授权才能继续；
- 一项能力可能从一个任务卡的“遗留问题”进入下一张卡，又从下一张卡的“遗留问题”继续传递；
- 多轮任务完成后，用户看到许多任务都标记为 `done`，却未必意识到其中仍存在尚未决定的功能缺口。

因此，问题的本质是**未实现工作缺乏与已完成工作同等明确的记录、汇报和追踪机制**。

本规范不要求 AI 为了完成率而越权，也不要求所有发现的缺口都立即实现。目标是确保：

> 任何未实现、被搁置、被缩小范围或因授权不足而暂停的功能，都必须被明确披露、解释、登记，并保留一个可追踪的处理状态。它不能只存在于任务汇报末尾的一句话中。

## 2. 设计原则

### 2.1 完成情况与未完成情况必须对称披露

任务汇报不能只围绕“做了什么”组织。必须同时说明：

1. 原任务要求了什么；
2. 哪些要求已经实现；
3. 哪些要求没有实现；
4. 未实现的原因是什么；
5. 未实现造成什么能力缺口或后续影响；
6. 需要用户作出什么决策；
7. 未实现事项将由谁、在什么条件下继续处理。

### 2.2 授权不足是阻塞原因，不是结案理由

“需要 Extend 授权”或“涉及 Rearchitect”只解释了为什么不能直接实现，**不代表该功能已经得到处理**。

AI 必须继续完成以下工作：

- 标识缺少的能力；
- 解释现有机制为何无法完成；
- 指明所需授权及其边界；
- 给出最小可行扩展方案；
- 说明批准、暂缓或拒绝分别会产生什么结果；
- 将事项登记到未决工作清单。

在没有获得授权时，AI 不得实现越界部分；但也不得把它从任务结果中隐藏或视为自然消失。

### 2.3 只阻塞越界部分，不无故停止整个任务

如果任务中只有一项功能需要额外授权，AI 应：

- 继续完成不依赖该授权的其他工作；
- 将受影响的功能单独标记为 `blocked_authorization`；
- 明确说明当前实现因此不完整的部分；
- 不得为了维持任务 `done` 状态而把该功能从原始需求中静默删除。

如果被阻塞功能是任务核心验收条件，任务不得被汇报为“全部完成”。

### 2.4 不把不同性质的未实现事项混为一谈

至少区分：

| 类别 | 含义 | 处理方式 |
|---|---|---|
| `blocked_authorization` | 功能需要更高权限，尚未获得授权 | 明确请求授权，进入待决清单 |
| `deferred` | 用户或计划明确决定以后再做 | 记录延期原因、触发条件和复审节点 |
| `out_of_scope` | 当前任务原本不要求实现，但执行中发现相关缺口 | 评估影响，决定是否立项 |
| `not_implemented` | 原任务要求或承诺的功能尚未实现 | 任务不能宣称完整交付，说明补齐计划 |
| `rejected` | 用户明确决定不实现 | 记录决定与影响，不再当作待授权事项 |
| `superseded` | 已被其他方案或任务替代 | 记录替代事项及链接 |
| `implemented` | 已完成且有验证证据 | 记录实现位置和验收结果 |

“暂时没做”不能同时代表上述所有情况。

## 3. 新增核心机制：未实现工作登记册

建议新增：

```text
working/
├── plan.md
├── tasks/
├── decisions/
│   ├── unresolved-work.md
│   └── decision-history.md
└── tmp/
```

### 3.1 `working/decisions/unresolved-work.md`

这是所有任务卡未实现事项的统一索引，避免每张任务卡只在自己的结果章节保留一条难以追踪的文字。

每个事项必须有稳定 ID，例如 `UW-001`。任务卡、计划、ADR 和后续实现任务均引用该 ID。

建议字段：

| 字段 | 必填 | 说明 |
|---|---:|---|
| ID | 是 | 稳定标识，例如 `UW-001` |
| 来源任务 | 是 | 首次发现该事项的任务卡 |
| 需求 / 缺口 | 是 | 尚未实现的具体能力，不写笼统标题 |
| 类型 | 是 | 授权阻塞、主动延期、范围外发现、未完成等 |
| 当前状态 | 是 | `pending_decision`、`blocked_authorization` 等 |
| 未实现原因 | 是 | 为什么当前不能或没有实现 |
| 所需授权 | 条件必填 | Modify / Compose / Extend / Rearchitect 的集合 |
| 影响 | 是 | 对产品能力、用户操作和后续任务的影响 |
| 建议方案 | 是 | 最小方案、涉及边界与验证方式 |
| 决策选项 | 是 | 批准、延期、拒绝或替代方案 |
| 依赖 / 关联项 | 否 | 与其他缺口、任务卡或 ADR 的关系 |
| 首次发现日期 | 是 | 防止事项长期隐藏 |
| 最近复核日期 | 是 | 记录最近一次重新评估 |
| 责任任务 / 触发条件 | 条件必填 | 后续在哪张卡处理，或何时重新评估 |

### 3.2 登记册状态

建议采用以下状态：

| 状态 | 含义 | 是否需要用户决策 |
|---|---|---:|
| `pending_decision` | 已识别，尚未决定是否处理 | 是 |
| `pending_authorization` | 已提出具体授权请求，等待批准 | 是 |
| `blocked_authorization` | 明确因未获授权而无法实现 | 是，或用户已决定暂缓 |
| `deferred` | 用户已决定以后处理 | 到达复审条件时 |
| `accepted` | 已批准处理，等待进入任务计划 | 否，需安排任务 |
| `in_progress` | 已进入实现任务 | 否 |
| `implemented` | 已实现并通过验收 | 否 |
| `rejected` | 用户明确拒绝该能力 | 否 |
| `superseded` | 已被其他事项或设计替代 | 否 |

不得把 `pending_authorization` 或 `blocked_authorization` 自动转成 `deferred`。延期必须有明确依据；用户没有答复不等于用户决定延期。

### 3.3 事项关闭规则

只有以下情况可以关闭一项未实现事项：

- 已实现，且有对应测试或验收证据；
- 用户明确拒绝，且记录了拒绝理由或适用范围；
- 已由其他明确事项替代，并建立关联；
- 用户明确决定不再需要该能力。

仅仅在下一张任务卡中没有再提到，不构成关闭。

## 4. 任务卡必须增加的结构

所有新任务卡都应包含独立的“需求覆盖与未实现项”章节。建议在 `working/tasks/000-template.md` 中新增：

```markdown
## 需求覆盖与未实现项

### 原始目标覆盖

| 需求 ID | 需求 / 验收点 | 状态 | 证据 / 说明 |
|---|---|---|---|
| REQ-01 | <具体能力> | implemented / partial / blocked / deferred | <文件、测试或原因> |

### 未实现 / 被搁置事项

| 未决 ID | 未实现能力 | 原因 | 所需授权 | 影响 | 后续处理 |
|---|---|---|---|---|---|
| UW-001 | <具体能力> | <为什么未实现> | Extend | <影响> | <决策或后续任务> |

### 本卡完成判定

- [ ] 原始目标和验收点已逐项映射，不存在未解释的缺项。
- [ ] 所有未实现事项均已登记到 `working/decisions/unresolved-work.md`。
- [ ] 所有授权阻塞均已说明最小授权范围和推荐决策。
- [ ] 任务状态没有掩盖仍未完成的核心验收条件。
```

### 4.1 原始需求不能在执行后被静默缩小

如果执行过程中发现原任务范围过大、需要额外权限或设计尚未冻结：

- 保留原始目标和验收点；
- 记录实际缩小后的执行范围；
- 逐项说明哪些要求被移出本次实现；
- 为移出的要求建立未决事项；
- 必要时修改验收标准，但必须记录修改原因和依据，不能只改任务卡正文而抹去原始要求。

建议任务卡增加：

```markdown
## 范围调整记录

| 日期 | 原始要求 | 调整后范围 | 原因 | 决策依据 |
|---|---|---|---|---|
| YYYY-MM-DD | <原始要求> | <本次不做 / 改为只读> | <授权 / 技术 / 计划原因> | <用户授权 / ADR / 任务决定> |
```

## 5. 任务状态与完成度必须分开表达

现有 `status: done` 容易被理解为“该任务相关能力已经全部实现”。实际上，它可能只表示任务卡最终选择的范围已经完成，而范围外能力仍在等待决策。

建议把两个维度分离：

### 5.1 任务执行状态

- `todo`
- `in_progress`
- `blocked`
- `done`

该状态回答：任务卡当前承诺的交付工作是否完成？

### 5.2 需求覆盖状态

- `complete`：原始需求与验收点均已完成；
- `complete_with_deferred_items`：任务约定范围已完成，但明确登记了后续事项；
- `partial`：原始目标仍有未完成部分；
- `blocked_by_authorization`：核心交付受授权不足阻塞。

建议在任务卡头部增加：

```yaml
status: done
coverage_status: complete_with_deferred_items
open_items:
  - UW-001
```

注意：`status: done` 只能表示本卡经过确认的交付范围完成，不能单独用来宣称更大功能目标完成。计划页面、阶段总结和用户汇报必须同时显示 `coverage_status` 与未决事项数量。

若未实现项仍属于本卡强制验收条件，则 `coverage_status` 必须是 `partial` 或 `blocked_by_authorization`，不能使用 `complete`。

## 6. AI 最终汇报规范

这是本次改进最重要的部分。

**未实现内容必须成为汇报主体中的独立章节，不能只在“遗留问题”末尾用一句话概括。**

每次任务汇报至少按以下结构组织：

### 6.1 交付摘要

说明本卡交付了什么、验证结果是什么，并给出任务状态与需求覆盖状态。

### 6.2 原始需求逐项覆盖

列出原任务目标和验收点，逐项标记：

- 已实现；
- 部分实现；
- 未实现；
- 已转为只读 / 暂缓；
- 已被其他方案替代。

不得只列已完成项。

### 6.3 未实现 / 被搁置的功能

每一项单独说明：

1. **功能是什么**：用用户能理解的实际操作描述，不只写内部技术名词；
2. **原本希望达到什么效果**：当前系统做不到什么；
3. **为什么没有实现**：缺少命令、Schema 不足、跨越授权、依赖未确定，还是明确不在范围；
4. **当前采用什么替代行为**：例如只读展示、人工操作、暂时无法编辑；
5. **影响是什么**：用户是否无法完成完整工作流，是否需要绕过 GUI，是否会影响后续任务；
6. **需要什么授权**：明确列出 Extend / Rearchitect 等权限集合；
7. **最小实现方案**：涉及哪些 crate、规范、UI、测试和文件范围；
8. **需要用户决定什么**：批准、暂缓、拒绝，或先做设计研究；
9. **登记 ID**：链接 `unresolved-work.md` 中对应事项。

### 6.4 验证与未验证边界

分别列出实际执行通过的测试、未执行测试、没有验证的真实环境行为。不能用构建成功替代功能完整性。

### 6.5 下一步与待决事项

单独列出：

- 本卡后续必须补齐的内容；
- 等待用户授权的内容；
- 已明确延期的内容；
- 当前建议的下一张任务卡。

### 6.6 禁止使用的模糊汇报方式

以下表述不能单独作为未实现项的说明：

- “Provider 编辑以后再做”；
- “需要 Extend”；
- “G1–G3 暂不处理”；
- “Source 编辑留待 M7”；
- “其余遗留问题见后续规划”。

这些表述可以作为摘要，但必须有完整事项说明、影响分析、授权边界和登记 ID。

## 7. 授权请求应转化为可决策提案

不能只告诉用户“需要授权”，而应提供可直接决策的提案。

每个授权阻塞提案至少包括：

| 项目 | 内容 |
|---|---|
| 当前能力 | 现有系统已经能做什么 |
| 缺失能力 | 用户实际无法完成什么操作 |
| 原因 | 为什么现有 Schema / 命令 / 架构不能支持 |
| 授权类型 | 需要的一个或多个工作模式 |
| 最小范围 | 具体 crate、文件、协议和功能 |
| 不包含内容 | 明确哪些相邻能力不会顺带实现 |
| 推荐方案 | AI 基于当前架构给出的建议 |
| 替代方案 | 只读、人工处理、延期或拒绝的后果 |
| 验收证据 | 如何证明该功能补齐且没有越权 |

### 7.1 推荐的决策选项

每项待授权工作应至少提供以下可选处置：

1. **批准最小范围**：授权 AI 按已列出的范围实施；超出范围仍需重新申请。
2. **先做设计研究**：允许 Inspect，不允许修改 Schema、领域模型或生产代码；提交 ADR / 影响分析草案。
3. **明确延期**：记录复审时间、触发条件或依赖任务；不再在每次汇报中重复请求授权，但必须持续显示未解决状态。
4. **明确不做**：将事项标记为 `rejected`，记录影响和决定依据。

不得把用户未回复当成批准、拒绝或延期。

## 8. `working/plan.md` 应提供未决工作总览

计划文档不能只列未来任务队列，也必须呈现已经发现但尚未安排的能力缺口。

建议新增章节：

```markdown
## 未实现功能与授权阻塞

| ID | 来源 | 功能缺口 | 状态 | 所需授权 | 影响 | 下一步 |
|---|---|---|---|---|---|---|
| UW-001 | 024 | Dependency Provider 编辑 | implemented | Extend + Modify | 已解除 | 025 |
| UW-002 | 021 | Interface / Contract 独立身份 | pending_decision | Rearchitect | 依赖仍按模块 ID 表达 | 先做设计研究 |
| UW-003 | 021 | Runtime / Service 容器 | pending_decision | Rearchitect | 运行服务只能被近似映射为结构节点 | 与 UW-002 联合分析 |
| UW-004 | 021 | Project Profile | pending_decision | Rearchitect | 无法表达完整 Profile 选择 | 独立评估 |
| UW-005 | 022 | ConfigValue 整数 / Float Wire 区分 | pending_decision | Extend（方案确认后复核） | Agent JSON 传输可能无法保留原始数值类型 | 单独设计 wire 语义 |
```

上表是根据当前评审已知事项形成的初始示意，正式迁移时必须逐项核对实现现状、历史授权与用户决策，不得直接复制成已经确认的事实。

计划页顶部还应显示：

- 未决事项总数；
- 等待授权数量；
- 已批准但未排期数量；
- 已延期数量；
- 超过约定复审日期的事项数量。

## 9. 阶段结项门禁

阶段结项不应只检查任务卡是否全部 `done`，还应检查未决工作是否被充分披露。

建议增加以下结项条件：

- [ ] 每张任务卡的原始目标和验收点都已逐项映射到实现结果；
- [ ] 所有部分实现与未实现项均有独立说明；
- [ ] 所有授权阻塞均有稳定 ID 和完整决策提案；
- [ ] 所有明确延期项均有延期依据与复审条件；
- [ ] 没有把未实现的核心验收条件隐藏在 `done` 状态中；
- [ ] `working/plan.md` 的未决工作总览与登记册一致；
- [ ] 阶段总结明确区分“已完成能力”和“尚未具备的能力”；
- [ ] 未经授权的事项没有被实现，也没有被静默删除。

如果阶段核心能力仍受授权阻塞，应报告“阶段交付受限”或“阶段部分完成”，不能仅凭剩余任务卡完成就报告阶段目标全部达成。

## 10. 历史任务回溯审计

这项机制不能只从新任务开始使用。建议对现有 `working/tasks/001`–`025` 做一次回溯整理。

### 10.1 回溯步骤

1. 逐张读取原始目标、范围、清单、验收和结果；
2. 提取任务卡中提到的所有限制、遗留、未实现、只读、暂缓、后续处理项；
3. 检查是否存在“任务卡目标提到，但结果没有对应实现证据”的能力；
4. 检查是否因 Extend / Rearchitect / 外部副作用授权不足而停止；
5. 检查后续任务是否真正解决，不能仅凭后续任务提到就标记完成；
6. 为仍未解决事项分配 `UW-*` ID；
7. 对已经实现的事项建立关闭证据和实现任务链接；
8. 对没有足够历史证据的事项标记 `historical_status_unknown`，不要推测当时的用户意图。

## 11. Change Manifest 与实现检查的配合

Change Manifest 主要回答“本次允许改什么”，未实现工作登记册回答“还有什么没有做、为什么没有做”。两者不能互相替代。

建议在任务卡和 Manifest 中建立关联：

```yaml
change:
  id: change.example
  intent: "完成指定功能"

  authorization:
    required:
      - modify
      - extend
    approved:
      - modify
      - extend
    evidence: "用户明确授权的记录或已批准任务"

  targets:
    - crates/example

  operations:
    - modify
    - extend

  scope:
    allowed:
      - existing_feature_implementation
      - new_command
      - tests
    forbidden:
      - domain_model_change
      - schema_version_change

  unresolved_items:
    - UW-001

  impact:
    expected_schema_changes: false
    expected_command_changes: true
    expected_design_baseline_changes: false
```

注意：这是建议字段结构，不代表当前仓库的 Manifest 校验器已经支持这些字段。正式采用前需要同步修改模板、解析器和校验规则，或先将其作为书面规范使用。

实现结束时，除了核对实际改动文件是否在 `targets` 内，还必须核对：

- 原始需求是否全部覆盖；
- 是否新增未实现项；
- 是否更新已有未决事项状态；
- 是否将已解决事项关联到实现证据；
- 是否存在超出授权而未执行的内容。

## 12. 给 AI Agent 的强制执行规则

建议将以下规则加入 `AGENTS.md`：

1. 开始任务时，除了读取任务目标和授权，还要读取当前未决工作登记册中与本任务相关的事项。
2. 实现过程中发现不能完成的能力，不得只在最终结果末尾写一句“需要 Extend / 后续处理”。
3. 对每项未实现能力，必须说明用户实际缺失的功能、阻塞原因、影响、所需授权和最小方案。
4. 未获授权时不得执行越界修改；但必须完成未决事项登记，并在汇报主体中独立披露。
5. 仅有部分功能被阻塞时，继续完成不受影响且已授权的工作。
6. 若未实现内容属于任务核心验收条件，必须将需求覆盖状态标为 `partial` 或 `blocked_by_authorization`。
7. 任务卡标记 `done` 时，必须同时提供 `coverage_status` 和 `open_items`；不允许只用 `done` 表示全部目标均已实现。
8. 用户没有回复授权请求时，保持待决状态，不得推断为批准、拒绝或延期。
9. 每次任务汇报必须包含“未实现 / 被搁置功能”章节；即使没有事项，也明确写“无”。
10. 阶段总结必须汇总所有未决事项，不得只总结已完成任务。

## 14. 实施顺序

建议分三个阶段落地，先修正信息呈现，再做自动化，避免一开始就引入过重的流程工具。

### 阶段 A：立即实施 — 汇报与记录制度

1. 修改 `working/tasks/000-template.md`，加入原始目标覆盖表和未实现项章节；
2. 修改 `AGENTS.md`，加入未实现功能显性披露规则；
3. 新建 `working/decisions/unresolved-work.md`；
4. 修改 `working/plan.md`，增加未决事项仪表区；
5. 对 024、025 和 021 的已知事项建立首批登记记录。

验收：以后任何任务即使因授权受阻，也不会只在汇报末尾留下简短备注。

### 阶段 B：历史回溯 — 找出已被搁置的能力

1. 审计 001–025 所有任务卡；
2. 搜索“遗留”“暂不”“只读”“后续”“需要授权”“不在范围”等线索；
3. 为每项未决功能补充影响与状态；
4. 验证后续任务是否真正实现；
5. 形成待用户决策的清单。

验收：所有已知未实现项都有去向；状态不明的明确标记，不以猜测关闭。

### 阶段 C：流程门禁 — 防止再次遗漏

1. 任务结束时校验原始需求覆盖表；
2. 检查所有未实现项是否登记；
3. 检查任务 `status` 与 `coverage_status` 是否一致；
4. 阶段结项时汇总未决工作；
5. 后续再考虑用 Schema 校验或脚本自动生成报告。

验收：任务卡、计划和最终汇报三处状态一致；未决事项不能因任务卡归档或编号推进而消失。

## 15. 最终决策建议

建议正式采纳以下五项规则：

1. **未实现事项必须单独汇报。** 不得只在“遗留问题”中简短带过。
2. **每项未实现功能必须登记。** 必须有稳定 ID、原因、影响、授权要求和后续状态。
3. **任务完成与功能覆盖分开。** `done` 不再单独代表所有相关能力都已实现。
4. **授权阻塞必须形成决策提案。** 说明批准、延期和拒绝的具体后果，而不是只说“需要授权”。
5. **历史任务必须回溯。** 对 001–025 中被简短记录的未实现能力重新检查，不能假定它们已经处理。

本次改进的重点不是要求 AI 做更多未经授权的工作，而是要求 AI 对没有做的工作承担同等程度的说明和追踪责任。

**目标状态：用户查看任何一张任务卡或阶段总结时，都能同时知道 AI 完成了什么、没有完成什么、为什么没有完成，以及还需要作出什么决定。**
